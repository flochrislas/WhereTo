# Proposal for an iPhone app

Start with WhereTo as a **Home Screen web app**. It already has a standalone web manifest, an Apple touch icon, English and Japanese routes, and a service worker. If App Store distribution is a product goal, build a SwiftUI edition around an **offline Shibuya guide**. A visitor could save a lunch shortlist before a trip, then filter places and read their Japanese names after losing connectivity at the station.

## An installable version with the current site

Open WhereTo in Safari, choose **Share → Add to Home Screen**, enable **Open as Web App** where offered, and tap **Add**. Provide these instructions in English and Japanese. On a physical iPhone, launch from the new icon, switch languages, open a place, follow its Maps link and return. Repeat with location denied to check the Shibuya Station fallback. After one online visit, try a previously opened search in airplane mode. The web app caches selected responses, so a fresh search can still need the network. [Apple’s Home Screen instructions](https://support.apple.com/guide/iphone/open-as-web-app-iphea86e5236/ios) · [WhereTo offline behavior](04-how-it-works.md#10-installable-app-and-offline-service-worker)

## A native edition for the App Store

A traveler should be able to browse the guide on the first launch in airplane mode. That gives the native edition a concrete purpose and addresses the minimum-functionality question Apple raises for apps built around a website. Review remains Apple's decision. [App Review Guidelines, section 4.2](https://developer.apple.com/app-store/review/guidelines/#minimum-functionality)

1. **Publish a small, versioned catalogue from Laravel.** The current results and details endpoints return Blade HTML. Add a read-only JSON export of public place fields, including stable IDs, category, names, localized tag labels, coordinates, scores, business status and shareable links. Keep IDs stable across reseeding so a saved lunch spot continues to point to the same place. Generate the export from the same data that powers the website. [Current routes](../source/routes/web.php) · [Data model](03-data-model.md)
2. **Prove the idea with restaurants.** Bundle one catalogue snapshot in an Xcode/SwiftUI project under a proposed `mobile/ios/`. Build a searchable list, tag filter, detail screen and on-device saved list. Show both names where available, offer directions in Maps and share the existing place URL. Request foreground location when the visitor selects nearby sorting. Calculate distance on-device and use the station when permission is denied.
3. **Refresh safely.** When online, download a newer snapshot, validate its schema and replace the local catalogue only after the download succeeds. Display the catalogue date. Keep saved entries identifiable when a business closes, mark its status, and exclude it from suggestions. Test an interrupted update and a reseed before extending the pilot to stores, bars and karaoke.
4. **Distribute a TestFlight build.** Use a Mac with Xcode, a bundle ID and an Apple Developer Program team. Ask testers to launch offline immediately after installation, find a restaurant by a Japanese tag, save it, relaunch and share its link. Check VoiceOver, large text and location denial on a real iPhone. For App Review, supply screenshots, support and privacy URLs, accurate privacy disclosures, and review notes explaining how to try the offline guide. [TestFlight](https://developer.apple.com/testflight/) · [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)

The native edition adds a second interface and a catalogue format that older installed versions must keep reading. Proceed beyond the restaurant pilot if offline discovery and saved places justify maintaining both. For visitors who primarily use the live site, the Home Screen version already offers the shorter path.
